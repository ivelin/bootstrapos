# Bet loop SOP v1.0.0 (for founders)
A simple way to test product ideas before you spend on them. Numbers in *italics* are starting points; adjust them as you learn.

## 1. The idea
- Every bet must relieve the one thing holding your company back right now.
- Test cheaply first, with simulated users, then with real people, then build.
- Nobody grades their own work.

## 2. The chain: bottleneck -> bet -> tests -> evidence
- **Bottleneck**: the one honest constraint stopping you this week. It's a field on your board, not a folder. It can change; note why when it does.
- **Bet**: an idea card that exists only to relieve the bottleneck. It opens with "Relieves: <bottleneck> because <reason>." If it can't say that, park or kill it.
- **Tests** (the card's initiatives): each has a premise (how it eases the bottleneck), a measure, and a kill line.
- **Evidence**: every file names its test id, so any result traces back to the bottleneck.
- **Weekly**: restate the bottleneck first. Hold or kill anything that no longer fits. If the bottleneck moved, re-rank before starting new work.

## 3. Where things live
| What | Where |
|---|---|
| Status | Your Bootstrap OS board. The only place status lives. |
| Evidence | One folder per bet in a storage service that survives losing your computer (Google Drive by default; Dropbox, OneDrive, S3 also fine). Local-only doesn't count. |
| Code | Your product repo. Code and pull requests only, no bet documents. |

## 4. Default folder layout (adapt freely)
```
<storage root>/Business/Bets/
  <company>/<idea>/
    00_README.md
    YYYY-MM-DD_1-design_<test-id>_bet-card.md
    YYYY-MM-DD_2-synth_<test-id>_<study>.md   (+ .csv/.json summary)
    YYYY-MM-DD_3-real_<test-id>_<test>.md
    YYYY-MM-DD_4-decision_<test-id>_<go|kill|pivot>.md
    YYYY-MM-DD_5-audit_<test-id>_<month>.md
  _archive/<company>/<idea>/
```
- Use your board's company and idea short names. Use `no-init` until a test id exists.
- 00_README.md is the index: the "Relieves:" line, card link, frozen-bars hash, file list. It points to the board for status. It's the only file you edit.
- Every other file is dated and never edited or renamed. A revision is a new dated file.
- Two files for the same stage on the same day: naming rule **TBD**.
- You can rename or move things, as long as: the board holds status, each bet has one folder the card links to, files are dated and append-only, bars are frozen with a hash on the card, and retired bets go to an archive.

## 5. Roles
One person or bot can hold several roles, but the tester never grades work they built or designed.
| Role | Does |
|---|---|
| Founder | Names the bottleneck; approves gates, spend, and anything sent to real people. |
| Board assistant | Keeps the board current; runs the weekly check. |
| Designer | Sets the success and kill bars before any spend; estimates odds. |
| Synthetic tester | Runs simulated-user tests and grades them. |
| Real-world tester | Grades real tests against the frozen bars. |
| PM | Ranks bets, plans and runs tests. |
| Builder + reviewer | Builds test artifacts and product; a reviewer approves code. |

## 6. Steps
1. Name the bottleneck. Write the bet card: problem, who it's for, limits (budget, margin, legal), expected impact, cost estimate, measurement window.
2. Set the bars: hypothesis, one main metric, minimum effect, sample size (≥*10*), stop date, guardrails, kill rule. Freeze them (§7).
3. **Synthetic test. Required, never skipped.** Use a judge model from a different family than the simulated users. A weak or inconclusive result means rerun or redesign, not advance.
4. Score: ROI = (impact × confidence) ÷ cost. Decide: advance, kill, or spend.
5. Build the cheapest real test first: waitlist, landing page, fake-door button, mock, manual version, or survey. Full build only after it passes, unless you write down why no cheaper test works.
6. Run it; grade PASS / FAIL / INCONCLUSIVE against the frozen bars.
7. At window end, record actual results and cost. Decide go, kill or pivot.
8. Pivot with the same main metric: same folder, new design file. New metric: new test id. Killed bets move to the archive after *30 days*.
- Raw simulated-user transcripts stay out of the evidence folder; record where they are and their hash. Exact location: **TBD**.

## 7. Freezing bars
Compute the sha256 of the bars file. Put the hash and date/time on the card and in 00_README.md. Changes after that need a new dated file. A grade only counts if the freeze came before the first spend.

## 8. Before testing with real people
Get explicit approval for anything sent out. Don't contact anyone twice or out of order. Track responses. Respect privacy and get a legal check where needed.

## 9. Measures (once you have a few bets)
Cost per bet, estimate error, real ROI, hit rate on the main metric, how well your odds predicted results (Brier score, after *10* bets), synthetic-vs-real gap, cycle time. Stop any bet that costs over *2×* its estimate unless you choose to extend it.

## 10. Monthly
- Re-check a few closed bets: does cost and grade still hold up from the raw data? Save it as a `_5-audit_` file.
- Change one rule at a time, say what metric should improve, and roll back if it doesn't within a month.

## 11. Growing into it
Your board assistant adds help as your evidence grows, one step at a time, only with your yes:
0. Board and weekly brief. 1. One bet with a measure and kill line. 2. Synthetic tester. 3. Real-world tester and cheap-test builder. 4. PM, once you have 2+ bets. 5. Builder and code reviewer. 6. Full loop: cost, audits, calibration (5+ graded bets).
No step skips the synthetic test.
